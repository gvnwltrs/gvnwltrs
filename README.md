Deep diving hardware access to drive better low-level control/understanding under the hood of high-level API. Basically, I'm re-defining my approach to cut-out the middle-man between "someone else's library/framework" and the hardware I need to talk to as much as it's feasible to do so. This is taking a low-level understanding from bare-metal/embedded/FPGA to apply that more generally as a "universal" programming approach for MMU-based architectures or OS-based systems that won't give you direct memory mapped I/O access. The theory is that many libraries abstract all this away, which is nice, but not so nice when you need to understand what your software is ACTUALLY doing on the hardware or from the CPU's and associated hardware's perspectives. 

Disassembly can of course give you some of that insight for what your code is doing or transformed into via the compiler/interpreter (byte code to interpreter runtime in the interpreter case) in terms of the instructions, but it's this plus the application of the insights of what the hardware is doing and what you'd like it to do more directly that is what is being chased down for me right now, and has resulted in sigficant clairity to how I approach software from this point forward. This is stemming from observations from industry and open source over the years where there has been, at times, heavy use or a subscription to Object-Oriented Programming as a default, with seemingly little to no awareness of approaches like functional programming, data-oriented programming, or just general hardware friendly code. Of course, modern hardware and memory resources have expanded to the point that thinking about the hardware when writing software is more of an afterthought if thought at all in some contexts, but just because one may have 1GB or 64GB of memory and a single or multi-core CPU, does not necesarilly mean that one should forget the fact that all the code that is written in a high-level language translates into machine code that runs on the hardware. 

It is my belief, that just because the hardware can take a thrashing with software that produces instructions that send the CPU on a wild hunt for this address and that, creating cache misses, pipeline flusing, missed predictions etc. where the hardware capabilities are so incredibly fast that one doesn't even notice it (at least until it scales), doesn't mean one should ignore the hardware. Software doesn't only have to make sense to the human, but also to the machine. And if one wishes to strike a balance in that way, then it seems reasonable that one has to find a way to ensure what they write in high-level code can make its way into the hardware to use it effectively/efficiently.   

Not a religion, but a way of thinking/doing that cuts through the abstraction as much as it can, or is reasonable to do so, to not have such a hard dependency on the libraries and frameworks that help, but also remove one away from the reality of what the code is doing underneath the abstractions and then on the hardware. This approach, thus far, has provided new opportunities for me and for how I approach ANY software, to include finding new ways to explore what's possible beyond the dependencies or comfort of another's library or framework. More recently, that's seemingly producing an emergent property for going beyond even what is documented or specified on paper, such that it provides me the flexibility to explore on my own without requiring a search engine or LLM in the majority of cases. Just a brain and a terminal. 

All-in-all, I'm defining MY particular approach to writing software no matter if it's embedded, bare-metal, kernel space, or user space applications, but in all cases with a hardware level "awareness" that should hopefully produce more straight-to-the-point software implementations that are clear not only to the human minds that read the code, but also clearer to the CPU that has to deal with them. Hopefully in the coming months, I can share that pattern more. Until then, it's just what I'm doing locally so my repo's may not reflect all that is actually being done right now.
